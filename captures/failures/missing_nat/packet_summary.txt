Missing NAT — reviewed packet evidence
======================================

Capture scope
-------------
Interface: any
Capture filter: GTP-U UDP port 2152 or ICMP
UE address: 10.45.0.5
Test destination: 8.8.8.8
Public evidence contains only the five controlled Echo Requests or request/
reply exchanges. Unrelated background ICMP was removed.

---------------

2. decapsulated Echo Request from 10.45.0.5 to 8.8.8.8;

There are five GTP-U uplink requests and ten visible inner/forwarded request
observations. There are zero ICMP Echo Replies and zero GTP-U downlink replies.

Interpretation:
The UE, gNB, N3 GTP-U tunnel, UPF decapsulation, and Linux forwarding path all
worked. The source address remained private 10.45.0.5 on the external path,
so the remote network had no usable return route.

Each of the five ICMP sequences produces six visible packets:

2. decapsulated Echo Request sourced by 10.45.0.5;
3. externally forwarded request after MASQUERADE source translation;
4. external Echo Reply to the translated address;
5. reverse-NAT Echo Reply addressed to 10.45.0.5;
6. GTP-U downlink packet carrying the Echo Reply to the UE.

Frames 1-6:   sequence 1 complete request/reply path

Frames 13-18: sequence 3 complete request/reply path
Frames 19-24: sequence 4 complete request/reply path
Frames 25-30: sequence 5 complete request/reply path

Interpretation:
Restoring the exact UE MASQUERADE rule restored all five return paths without
restarting the UE, gNB, or PDU session.

Comparison
----------
NAT absent:
  GTP-U uplink -> UPF decapsulation -> private source forwarded -> no reply

NAT restored:
  GTP-U uplink -> source translation -> external reply -> reverse translation
  -> GTP-U downlink -> UE

The unchanged 5G session and immediate recovery localize the failure to N6/
Linux return-path translation, not registration, PDU-session establishment,
PFCP, GTP-U, or basic forwarding.
